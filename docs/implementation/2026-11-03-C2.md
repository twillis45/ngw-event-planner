# C2 — RSVP capability truth — November 3, 2026

Base examined: `d22a96837cfc3361526739883c7a7f7edbf03126`. November 3 recertification and one-week plan were read from `origin/main-2utz0n`; no audit status was silently rewritten. This log records implementation evidence, not a Stage-9 ruling.

## Reproduction and root cause

- `isRsvpApiConfigured()` proves only that a backend base URL was baked into the build. The `services` release profile includes it while omitting Supabase/auth configuration.
- HostV2 creation and edits call canonical `events.saveEvent` only with a session. Account hydration also uploads eligible existing local events on sign-in. The `services` visitor therefore has a local event, not a `public.events` row.
- The backend public invite and RSVP endpoints resolve only `public.events.data.rsvpCode`; they do not read the visitor's local store. A configured service cannot publish an event.
- Host sharing used configuration as public capability, and native sharing bypassed even that warning. QR and draft URLs were unconditional.
- Local preview resolution itself works: `eventPool.ALL_SAMPLES` includes `CUSTOM_EVENTS_AT_LOAD`. The supplemental legacy `LS_CUSTOM` read in InviteV2 was not the defect and was preserved.
- Local submission initialized `delivered=true` even without an API. A failed local outbox write plus no API could also celebrate a reply that was neither sent nor saved.

## Canonical change

`checkRsvpCapability(event)` uses the existing public resolver and requires the exact event ID and invite code to be returned. Missing configuration, unpublished/mismatched rows, and lookup uncertainty fail closed. Lookup has an eight-second abort boundary. No capability is persisted and no alternate event writer was added.

Every host native-share/clipboard/QR path now checks public capability first. Invitation/brief/nudge drafts include a URL only after that check; otherwise their existing plain-text fallback remains available. Per-person SMS/email handoffs also check before embedding a URL. Guest forwarding uses the same check. A local preview labels online delivery unverified.

Local replies initialize `delivered=false`; only the canonical client accepting explicit `{ok:true}` makes it true. Local outbox success is measured before claiming a local save. When neither delivery nor local save succeeds, the form remains with an error and no submitted-conversion event. Existing queue keys, retry lifecycle, idempotency, auth, event persistence, and prioritization remain unchanged.

## Finding disposition and release dependency

`RSVP-LIVE-1` engineering false-promise paths are addressed locally, including native sharing, QR, outward drafts, guest forwarding, and local-submit confirmation. The RSVP half of `TRUST-1` in the creation reveal is owned by the parallel Creation lane; this commit does not close that finding by itself.

The one-week plan's proposed API+Supabase+session+cloud-ID predicate was insufficient evidence of publication: even a signed-in save can be pending, failed, or point at the wrong backend. This implementation checks the actual public resolver instead.

**D1 remains a product/owner ruling:** genuinely operational new online RSVPs on the paid release candidate require the authorized account/cloud lifecycle. This commit does not enable `live`, force sign-in, publish anonymous data, mint a privileged credential, or claim a deployed round trip. Before closing the release gate, verify a signed-in saved event resolves publicly, a stranger submits, and the owner reads that reply back on the release candidate deployment.

Temporary local Playwright configs, dependency symlinks, build outputs, and raw test-result directories are excluded from the commit. The committed specs run through the existing canonical harness; `rsvpLocalReply.spec.mjs` deliberately uses its configuration-free synctest server on port 5244.
