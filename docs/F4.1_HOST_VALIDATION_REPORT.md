# Sprint F4.1 — Host Experience Validation Report

**Date:** 2026-07-04
**Method:** Live browser walkthrough (real event creation, real clicks) + source-code verification of every claim. No assumption taken from passing Jest tests.
**Posture:** Brand-new host, zero prior context.

---

## Executive Summary

F4's stage-generation logic is correct and well-tested in isolation. **It is almost entirely unreachable in the running product.**

Three independent defects compound into one outcome: **most hosts never see intelligent output, and the ones who do only see half of it.**

1. **Wrong reader wired.** `AssembleReveal` calls the *old* `eventIdentity()` presentation reader (meaning/honoree projection), not the *new* Sprint A `resolveEventIdentity()` engine. None of the fields F4's stage-builders expect (`primaryEventType`, `isCompound`, `ceremonyComponents`, `confidence`, etc.) exist on the object it actually receives. They are all `undefined`.
2. **The reveal doesn't fire for 4 of the 5 required scenarios.** Whether `AssembleReveal` renders at all is gated by `event.type`'s taxonomy family (`home_hosted` vs `host_driven`). Birthday, Retirement Party, Family Reunion, and the 50th Birthday + Military Retirement flagship are all `host_driven` → **the reveal never mounts.** Only Crab Feast (`home_hosted`) reaches it.
3. **Even where it fires, explainability is invisible.** `why`, `status`, `nextDecision`, `confidenceLabel`, and `sourceEngines` are computed correctly by `buildAssembleRevealStages()` but the rendering code in `AssembleReveal` only displays `title` and `what`. The entire "why this matters" layer — the stated point of F4 — never reaches the screen.

Verified live: creating a real Birthday event and a real Crab Feast event in the running app, with screenshots, DOM inspection, and source tracing for the other three scenarios (their code path is deterministic and doesn't depend on runtime state, so tracing is conclusive without needing to click through the UI).

**Would a brand-new host trust this enough to continue? No** — see the closing verdict.

### How scenarios 1, 2, 3, 5 were verified without needing a click-through
`evIsHost` (App.js:44233) is computed as `intakeFamilyConfig(ev.type).recordKind === 'event'`. This is a pure function of `ev.type` against a static taxonomy table (`eventTaxonomy.mjs`). I confirmed by direct table lookup:
- `Birthday` → `family: 'host_driven'` → `recordKind: 'client'` → gate fails
- `Retirement Party` → `family: 'host_driven'` → gate fails
- `Reunion` → `family: 'host_driven'` → gate fails
- `Crab Feast` → `family: 'home_hosted'` → `recordKind: 'event'` → gate passes

This is deterministic — no runtime state changes the outcome. Scenario 3 additionally never reaches identity resolution because Sprint A's engine isn't wired at all (see Finding 1).

## Detailed Walkthrough Evidence

### Birthday Party (Live)
1. Clicked **+ New event** → cold-open "What are we planning?" — good, calm entry.
2. Typed "Birthday" in the type search → selected it.
3. Saw a genuinely good preview card: *"A birthday — a moment that matters... 7-step plan · a 6-item shopping list, sized to your count · 6 key decisions"* with a milestone checklist. **This is honest, specific, pre-commitment proof of understanding** — better than anything AssembleReveal currently shows.
4. Picked date (Aug 4), entered guest count (40), clicked **Create event**.
5. **Landed directly on `EditorialCover`** ("You're hosting My Birthday") — no AssembleReveal at any point.
6. Clicked through to HostHome: shown its own baked-in "I've made a head start" narrative with a shopping list count and two ready items.

**Finding:** There are now **three separate "we did the work" moments** in this product — the Step-2 preview card, `EditorialCover`, and HostHome's own "head start" copy — and AssembleReveal (which F4 enhanced) is a *fourth*, and for Birthday it's the one that never shows up. This is not "no duplicate reveal flow" (an explicit F4.1 acceptance bar) — it's the opposite: overlapping reveal-like moments with inconsistent intelligence behind each.

### Crab Feast (Live)
1. Same intake flow, good preview copy ("Let's build a plan that does this day justice" / 9-step plan, 10-item shopping list, 5 key decisions).
2. Left guest count blank this time to test the blocker path.
3. Clicked **Create event** → **AssembleReveal did fire this time.**
4. Screen showed:
   - "SETTING UP MY CRAB FEAST" / "Your plan is ready."
   - Card 1: **"Guest Count" / "How many guests?"** ✓
   - Card 2: **"Building Your Day" / "5 moments, hour by hour."** ✓
5. No "Your Event" identity card at any point — it silently never rendered (no console error; `buildIdentityStage` returned `null` because the wired `eventIdentity()` reader returned `null` — no meaning/honoree captured at intake, which is normal and expected for every fresh event).
6. Clicked "Open my event" → HostHome.
7. **HostHome directly contradicted the reveal.** The reveal marked "Building Your Day" ✓ complete. HostHome's "Coming up later" section showed **"Food & drinks — We'll help with this once guests are in"** as a *dormant, not-yet-available* section, and "Anyone you're hiring" also dormant. The reveal implied progress; HostHome implied nothing had started.

**Finding:** This is a direct violation of the F4.1 acceptance bar *"Nothing contradicts."* A host who watched the reveal build their day would reasonably expect to see that reflected in HostHome, not a "we'll help with this later" deferral.

### 50th Birthday + Military Retirement (Traced, not clicked — see justification above)
- There is no free-text description field anywhere in intake. The only mechanism for a "compound" event is a structured `type` + `secondaryType` picker (pre-existing, unrelated to Sprint A).
- Even using `type=Birthday, secondaryType=Retirement Party`, `secondaryType` is only consumed by `occasionBlurb()` (a cosmetic sentence) and vendor-category aggregation (`vTypes` arrays at lines ~11298, 12034, 12068, 12187, 39734). **It is never passed into `playbookFoodPlan`, `effectiveRos`, or any Sprint A engine.** The timeline and food plan will silently use the *Birthday* playbook only, unaware a retirement is happening at all.
- Sprint A's `resolveEventIdentity()`, `resolvePersona()`, `shellResolver()` — the 55-test, fully-passing engines from the earlier sprint — have **zero call sites outside their own test files** anywhere in `src/`. They are orphaned code.
- There is no "Military Retirement" playbook. `retirementParty.js` (200 lines) is well-written for a *civilian career* send-off (surprise, toast, tribute, bar strategy) but contains **zero** mentions of: flag folding, 21-gun salute / rifle volley, color guard, dress uniform vs. civilian dress-change, military chaplain, taps, or base/post logistics (gate access, parking for a change-of-command-adjacent event).
- Net result: even if a host perfectly describes this event, the product cannot currently produce a merged ceremony+celebration plan, cannot detect the compound structure, and has no domain content for the military half regardless.

**This is the flagship scenario from Sprint A, and it is the least functional of the five today.**

## Military Ceremony Specifics — Research Candidates

The system does **not** naturally understand any of the following for the flagship scenario, because no combination of existing code paths connects free text (or even structured secondaryType) to ceremony-specific content:

- Formal ceremony sequencing (arrival, invocation, remarks, awarding, closing)
- Celebration-vs-ceremony transition logistics
- Guest transitions (who attends both halves vs. one)
- Food timing relative to ceremony (no eating during, reception after)
- Cake timing (birthday element layered onto a formal event)
- Photography needs (ceremony formal portraits vs. candid celebration)
- Speeches/tribute sequencing across two distinct emotional registers
- Military traditions generally (rank protocol, saluting customs)
- Flag folding / color guard / rifle volley protocol
- Dress code changes between ceremony and celebration
- Parking (military installations often have separate access/protocol)
- Timeline conflicts between formal ceremony pacing and casual party pacing

**Actionable research candidates:**
1. Author a dedicated "Military Retirement Ceremony" playbook (or ceremony-overlay module) with the above content, gated by explicit user confirmation ("this includes a military ceremony"), not silent inference.
2. Wire `event.secondaryType` (already collected!) into `playbookFoodPlan`/`effectiveRos` as a genuine merge input — this is the cheapest fix since the data is already captured at intake and simply isn't used downstream.
3. Decide, as a product question, whether compound detection should come from free-text parsing (Sprint A's approach) or from the existing structured `secondaryType` picker (already shipped, already in the UI) — running both in parallel risks a permanent architecture split.

## Top 20 Findings (ranked)

1. **[CRITICAL / Architecture]** `AssembleReveal` calls `eventIdentity()` (old meaning/honoree reader) instead of Sprint A's `resolveEventIdentity()`. Every field F4's stage builders read is `undefined`. *Fix: rewire the import + call site in App.js line ~22456.*
2. **[CRITICAL / Workflow]** 4 of 5 required host scenarios never trigger `AssembleReveal` at all, gated by an unrelated taxonomy field (`recordKind`). *Fix: decide whether F4 should fire for `host_driven` types too — almost certainly yes.*
3. **[CRITICAL / Bug]** `why`, `status`, `nextDecision`, `confidenceLabel`, `sourceEngines` are computed but never rendered in `AssembleReveal`'s JSX. *Fix: 15-30 min — add the missing spans.*
4. **[CRITICAL / Trust]** HostHome directly contradicts what the reveal just showed as "done" (Crab Feast: Timeline ✓ in reveal, Food "later" in HostHome). *Fix: audit HostHome's "Coming up later" gating against the same data the reveal used.*
5. **[Architecture]** Sprint A's `resolveEventIdentity`/`resolvePersona`/`shellResolver` (55 passing tests) have zero production call sites. Fully-built, fully-tested, entirely orphaned.
6. **[Architecture]** Three (soon four) overlapping "we did the work for you" surfaces exist: intake Step-2 preview card, `EditorialCover`, HostHome's own head-start copy, and `AssembleReveal`. None share a data source or vocabulary.
7. **[Architecture]** `event.secondaryType` is captured at intake but only feeds a cosmetic sentence (`occasionBlurb`) and vendor-category lists — never timeline, food, or risk generation.
8. **[Intelligence]** No "Military Retirement Ceremony" playbook exists; the closest playbook (`retirementParty.js`) is civilian-only and well-written but has zero ceremony-protocol content.
9. **[Copy / Bug]** If wiring were fixed but the fallback default weren't, the identity card's fallback string reads **"A event."** — broken grammar, will ship the moment #1 is fixed unless caught.
10. **[UX]** Risk Preview stage has never been observed to fire in any live scenario tested; its trigger conditions (compound + specific date windows) are unreachable given findings #1/#2.
11. **[UX]** Vendor stage never observed live; same root cause.
12. **[Decision Support]** Of 4 designed blocker types, only `guest-count-confirmation` is reliably reachable in practice.
13. **[Workflow]** Food/Shopping stages are gated behind guest count being entered — meaning a host who takes the fastest path through intake (skip guest count) sees fewer, not more, assembled stages.
14. **[Quick Win / Copy]** Timeline stage copy ("5 moments, hour by hour") is a count, not a preview — doesn't read as "this is YOUR day," reads as a generic placeholder.
15. **[Trust]** Because Identity never renders, no host in either live test ever saw proof the system read their specific input — the single most important trust moment in the F4 design never happens today.
16. **[Performance]** No performance issues observed — reveal animation is smooth, fires once, no lag.
17. **[UX]** Intake's Step-2 preview card ("What I'll set up for a Birthday" with a real milestone checklist) is *better* activation copy than anything AssembleReveal currently shows, and it happens before the event is even created. Worth studying as the template for what Identity-stage copy should feel like.
18. **[Bug]** `useFoodPriceFactor` is called with `null` region context inside `assemblePlanningDomains`, silently dropping regional cost sensitivity that the original hardcoded stages had via `useFoodPriceFactor(ev, profile)`. Minor accuracy regression versus pre-F4 behavior.
19. **[Architecture]** No mechanism exists to reconcile the structured `secondaryType` compound path with the free-text Sprint A compound path — a host using either one gets a completely different (and currently equally non-functional) experience.
20. **[Quick Win]** `console.error` calls in `assembleRevealEngines.js` will appear in production browser consoles on any tier failure — should route through the existing Sentry/`captureError` integration instead of raw `console.error`.

## Final Verdict

**"If I were a brand-new host planning this event, would I immediately trust this product enough to continue?"**

**No.**

The intake experience is genuinely good — the Step-2 preview cards are honest, specific, and build real confidence before the event even exists. That part I'd trust.

But the moment I create the event, the product's promised "I understood you" moment (AssembleReveal) either doesn't appear at all (4 of 5 scenarios) or appears without the one thing that would earn trust — proof it read my specific event (Identity never renders) — and then, where it does appear, it contradicts itself one screen later (Crab Feast: "your day is built" → "food comes later").

A brand-new host would not notice the missing architecture. They would notice the contradiction. That's the moment trust breaks: being told something is done, then immediately being told it isn't.

**What would need to be true for the answer to be yes:** the four critical blockers fixed, re-tested live exactly as done here, with the Identity stage actually rendering the specific thing the host typed, and HostHome not walking back what the reveal just promised.
