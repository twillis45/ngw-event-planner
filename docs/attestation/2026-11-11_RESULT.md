## Uploaded files: a permissions hole, found 11/11/2026 about 7:25 AM EST

The owner's read-only storage check (one query over `storage.objects`,
`storage.buckets` and `pg_policies`) returned:

- `event-files`: private, no size limit, any file type; **23 files, 31 kB**,
  oldest 6/2/2026, newest 7/22/2026.
- Seven policies on `storage.objects`, every one checking only
  `bucket_id = 'event-files'`:
  - `read_anon` (SELECT, anon) — **anyone holding the public key, which ships
    in the live bundle, can list and download every file**;
  - `upload_anon` (INSERT, anon) — anyone can upload anything;
  - "Planners can delete their own files" (DELETE, authenticated) — **any
    signed-in user can delete any file**; "their own" is in the name only;
  - `read_authenticated`, `upload_authenticated`, "Planners can read their
    own files", "Planners can upload their own files" — the same, bucket-wide.

This is what the policies allow; nothing here shows that anyone used it.

**Fix:** `supabase/migrations/022_event_files_owner_scoped.sql` drops all
seven and allows: reading by the uploader or a member of the event's studio;
uploading only under your own user id while signed in; deleting only your own
files. Nothing for anon. The bucket also gets the app's own limits (10 MB;
PDF, images, Word). The pack gains three rows (`event_files_anon`,
`event_files_scoped`, `event_files_bucket`) that FAIL until 022 is applied,
and its migration rows now expect 001–022.

**Side effect until the app change merges:** the live app files uploads under
an id that is not the signed-in user's and asks to overwrite, so after 022
uploads on the live site are refused. The branch fixes both (`upsert: false`,
the session's user id, and "Sign in to attach files." for a signed-out host).
Attaching a vendor contract is the only upload in the app; the newest file is
from July.
