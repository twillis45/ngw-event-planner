Tested · real

One fact, more than one owner

Found by scanning 402 modules for exported names owned by two or more files, then importing both sides of every hit and comparing the values.

authHeaders() real · capped 9 copies · 3 behaviours · capped

The module that exists to own this is apiAuth.js. Three files import it. Six roll their own. Fingerprinting each definition shows five genuinely different implementations, not nine copies of one.

adminApi.js  rsvp.js  vendorBrief.js  commApi.js   7a0d55c1fd43
kas.js       kcr.js                                165f054f6840
research.js                                        fdfac9575715
orchestratorClient.js                              7dc5d329dd95
apiAuth.js   ← the owner, used by 3 modules      b6bc60e0c4c3

Read all nine before touching any. Five fingerprints, but only THREE behaviours — two of the pairs differ by nothing but a comment (/* fall through to token */ against /* fall through */).

A  rsvp · vendorBrief · commApi · adminApi
     Authorization + X-Planner-Token, no Content-Type in the helper
B  kas · kcr · research
     Content-Type + Authorization + X-Planner-Token
C  apiAuth · orchestratorClient
     Content-Type + Authorization, and NO token

Group A's missing Content-Type is not a missing header: all four set it at the call site. Checked, because a POST with a JSON body and no Content-Type would have been a real defect hiding inside the duplication. It is not there.

Group C omits the token deliberately, and says so. apiAuth writes “unauthenticated — backend will 401” in its catch where the others write “fall through to token”. Opposite intents, both authored. So the obvious fix — move the six onto apiAuth — would remove the transition fallback from seven files: a no-op in production, a behaviour change in local dev.

The credential itself is gated correctly, in one place: scripts/validate-production-config.mjs and the deploy workflow keep the variable out of browser builds. There is no leak. What is left is a maintenance cost with no live defect behind it, against the widest blast radius in the codebase — every API client in the app.

CAPPED, NOT FOLDED, 2026-09-24. authHeadersDoesNotGrowAgain fails if a tenth copy appears, and pins the real consolidation target as a number: seven files decide to attach the credential, one file prevents it. The debt is registered and stopped from growing; paying it waits for a reason better than tidiness.

SYNC_STATUS · SYNC_STATUS_LABEL · getEventSyncStatus withdrawn on testing 2 questions, not 2 answers

This was listed as real. Reading both modules and both consumers showed it is not. They do not answer the same question, so there is no single fact with two owners.

api/syncState.getEventSyncStatus(event)
    reads PER-EVENT evidence — is a write queued, did the last
    attempt error, is there a success stamp
    → local-only | pending | synced | sync-failed

syncStatus.getEventSyncStatus(event, sessionCtx)
    asks nothing about the event; reads three booleans the CALLER
    supplies about the SESSION
    → sample | local-only | server-synced | unknown

The second is older and coarser, and its unknown exists precisely because it has no per-event evidence — the stamps and queue maps the first one reads are that evidence. Calling them two vocabularies for one concept was wrong.

The one consumer I expected to be misled is not. The admin console's sync table is gated to NODE_ENV !== 'production' and labels itself “Dev/QA only · Derived from session state”, printing the session values it used. Every row showing the same status is the disclosed consequence of a session-derived status, not a control lying about what it does.

Nothing to fix. The remaining issue is the shared export NAME, and renaming it means editing src/App.js, which is frozen to security and data-loss fixes. A labelling collision is neither.

LS_CUSTOMS real 1 key · 2 declarations

The same localStorage key string, declared in two files. They currently match.

src/lib/customEventStore.js:30   'ngw-hostv2-custom-events'
hostv2/src/eventPool.js:37       'ngw-hostv2-custom-events'

If either one ever changes, the host shell and the store read different buckets and every event a host created disappears. hostv2 already imports freely from @app/lib, so the second declaration has no technical reason to exist. Cheapest to fix, worst if it breaks.

feedback() real 16 bands vs 3 guesses · fixed

src/lib/feedback.js is a 16-function haptic and tone vocabulary — feedbackCommit, feedbackSeal, feedbackLock, feedbackHeart, feedbackBudget — used by the CRA shell. HostShellV2.jsx:5621 defines its own feedback(kind) with three patterns. Confirmed absent from the host bundle by rollup.

Three differences, and all three were defects. The shell's default duration was 10ms — below the perceptible floor the engine documents in its own words: “a 9ms buzz technically fires but the motor renders nothing, so a haptic you can't feel is pointless.” Eight of the shell's thirteen feedback calls used that default. They fired, and nobody felt them. It also ignored prefers-reduced-motion for vibration, in a file that honours it for animation, and the ngw-haptics opt-out never reached the shell at all.

The one thing the shell got right — muting sound silences the chime and leaves haptics alone, from a motion re-audit — is kept by the fold rather than lost to it: the engine already separates ngw-haptics from ngw-sounds. That is the opposite of authHeaders, where folding would have destroyed a deliberate difference, and it is why this one was folded and that one capped.

FIXED 2026-09-24. The shell delegates to haptic(), and the intent map lives with the bands so the two cannot drift. The chime stays local on purpose — playMessageChime is the shell's message tone, not the engine's. Red-proofed on both halves separately: a typo'd band name is a silent downgrade, since haptic() falls back rather than throwing, and a band below the floor fails on its own.

Tested · my error

The one I got wrong

isPastEvent my test was wrong

My probe showed true from one and false from the other on the same 2020 date, which looked like two implementations disagreeing about whether an event is past. Then I read them.

dates.js          isPastEvent(dateString, now)
closeoutIntel.js  isPastEvent(event, asOf)
                    → resolves spanEnd(event) for multi-day events
                    → calls dates.isPastEvent, imported as isPastCalendarDay

It is a wrapper, and the author renamed it on import specifically to prevent this confusion. My test passed an object where a string was expected. Not a defect — a bug in the instrument. Third time tonight that a hand-written measurement was wrong, so it is recorded rather than dropped.

Sequence

Order to fix them

  1. LS_CUSTOMS — done 2026-09-24. eventPool re-exports the key from the store that writes it, and a structural guard fails if anyone declares a second one.

  2. authHeaders — capped 2026-09-24, deliberately not folded. Group C omits the planner token on purpose, so the obvious fold would change behaviour in seven files. A guard now fails on a tenth copy. Pay it down when auth actually changes, and do it by parameterising apiAuth rather than deleting the fallback.

  3. feedback — done 2026-09-24. The shell delegates to the engine's tuned bands, and the mute-versus-haptics rule survived because the engine already separated those keys. Eight call sites went from an imperceptible 10ms to a band a host can actually feel.

None of this is on the engine priority list. It is separate work, and smaller than it looked before testing.
