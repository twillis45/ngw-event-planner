One fact, more than one owner

Found by scanning 402 modules for exported names owned by two or more files, then importing both sides of every hit and comparing the values.

authHeaders() real 9 copies · 5 variants

The module that exists to own this is apiAuth.js. Three files import it. Six roll their own. Fingerprinting each definition shows five genuinely different implementations, not nine copies of one.

adminApi.js  rsvp.js  vendorBrief.js  commApi.js   7a0d55c1fd43
kas.js       kcr.js                                165f054f6840
research.js                                        fdfac9575715
orchestratorClient.js                              7dc5d329dd95
apiAuth.js   ← the owner, used by 3 modules      b6bc60e0c4c3

They differ in substance. apiAuth sends only the Supabase bearer token. The four-file variant also attaches X-Planner-Token. Seven files independently read REACT_APP_PLANNER_TOKEN, each with its own comment calling it a transition or dev fallback.

Checked before saying anything alarming: the credential is gated correctly. scripts/validate-production-config.mjs and the deploy workflow both keep that variable out of browser builds, in one place. There is no leak. The cost is that the decision to attach a credential is made in seven files and prevented in one, and any change to how auth works means finding nine implementations.

SYNC_STATUS · SYNC_STATUS_LABEL · getEventSyncStatus real 2 vocabularies

Two modules describe the same thing — whether an event has synced — and agree on exactly one value.

api/syncState.js   local-only   pending        synced          sync-failed
syncStatus.js      local-only   sample         server-synced   unknown

the one shared value, labelled twice:
  api/syncState   "On this phone — not synced yet"
  syncStatus      "Local only"
  • hostv2 reads api/syncState.js
  • src/App.js and AdminConsole.jsx read syncStatus.js

Same event, two answers about its sync state, and two different sentences for the one state they share.

LS_CUSTOMS real 1 key · 2 declarations

The same localStorage key string, declared in two files. They currently match.

src/lib/customEventStore.js:30   'ngw-hostv2-custom-events'
hostv2/src/eventPool.js:37       'ngw-hostv2-custom-events'

If either one ever changes, the host shell and the store read different buckets and every event a host created disappears. hostv2 already imports freely from @app/lib, so the second declaration has no technical reason to exist. Cheapest to fix, worst if it breaks.

feedback() real 16 functions vs 3 patterns

src/lib/feedback.js is a 16-function haptic and tone vocabulary — feedbackCommit, feedbackSeal, feedbackLock, feedbackHeart, feedbackBudget — used by the CRA shell. HostShellV2.jsx:5621 defines its own feedback(kind) with three patterns. Confirmed absent from the host bundle by rollup.

The flagship surface has a coarser vocabulary than the engine already owns, so a seal, a lock, a heart and a budget warning all feel the same. The host version does carry a real audit finding the shared module may not — that muting sound must not kill haptics — which argues for folding that rule up, not for keeping two.

Same name, different thing

Five more names are owned twice. Importing both sides showed they hold unrelated facts. These are naming hazards, not duplicate truth, and none of them needs fixing.

NameOwner A holdsOwner B holds
DECISION_TYPES audit event kinds — vendor_selection, budget_reallocation, planner_override the schema shape enum — pick-one, multi, count, yes-no, free
PHASES lifecycle phases — planning, research, booking, … closeout timeline buckets — 12 Months Out, … Week Of, Final Days
KNOWLEDGE_DOMAINS playbook families with descriptions and member types a flat list of subject tags
ENGINES governed price models surface labels for the registry
PROVIDER_FAMILIES 7 operational groupings with labels and member providers 16 authority families, validated by makeProvider

The last one deserves a note: three of campaign's family ids are not in the providers list, and providers throws on an unknown family. Traced it — campaign never calls that validator, so the two lists sit on different axes and nothing breaks.

Tested · my error

The one I got wrong

isPastEvent my test was wrong

My probe showed true from one and false from the other on the same 2020 date, which looked like two implementations disagreeing about whether an event is past. Then I read them.

dates.js          isPastEvent(dateString, now)
closeoutIntel.js  isPastEvent(event, asOf)
                    → resolves spanEnd(event) for multi-day events
                    → calls dates.isPastEvent, imported as isPastCalendarDay

It is a wrapper, and the author renamed it on import specifically to prevent this confusion. My test passed an object where a string was expected. Not a defect — a bug in the instrument. Third time tonight that a hand-written measurement was wrong, so it is recorded rather than dropped.

Sequence

Order to fix them

  1. LS_CUSTOMS — one line, and it is the only one with data loss behind it. Import the key instead of redeclaring it.

  2. SYNC_STATUS — two label sets for one state is something a host can actually see. Fold to one owner.

  3. authHeaders — largest, but the owning module already exists. Move the six onto apiAuth.js and keep the planner-token decision in one place.

  4. feedback — carry the mute-versus-haptics rule up into the shared module, then delete the host copy.

None of this is on the engine priority list. It is separate work, and smaller than it looked before testing.
