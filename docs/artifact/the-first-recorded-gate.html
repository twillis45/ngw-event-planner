Marketing & promotion — the parallel track

It starts at stage 2, not after Deploy

Positioning that arrives after the build is not positioning; it is an apology. Every phase below is a claim-verification gate wearing a marketing name, and the failure is always the same shape: an asset that exists mistaken for an asset that works. This track does not block build stages — it gates the next marketing phase and the spending of money.

1

Positioning — runs at stage 2

The acquisition thesis written down as something that can turn out false, with its constraints reaching design while design can still absorb them.

Exit: the thesis names the acquisition unit, the single thing a stranger must understand from it, and what result would falsify it. A thesis nothing could disprove has not been written yet.

  • ✓ Competitive reads exist and are specific — the closest funded competitor counts inventory, not readiness; nobody in the set has a readiness rollup.
  • Write the acquisition thesis as one falsifiable sentence. Not yet written — a competitive read is not a thesis.
  • Name the acquisition unit: the one screen or clip a stranger actually sees first.
  • State what result would falsify it, before any test runs.
  • Hand the positioning constraints to design as requirements, not preferences.

Invert the funnel rather than forecasting it. The question is not what we might earn but what we would have to earn for this to work — required revenue per paid host = acquisition cost ÷ net of platform fees, per geography, with cost and revenue drawn from the same population.

Exit: at least one named geography where achievable revenue per paid host exceeds the required figure, sourced rather than assumed. A NO-GO here is a real result and stops the track.

  • ✓ Price designed: the $39 One-Event Pass. Billing built and dormant behind five preconditions.

  • Name one geography that clears, with cost and revenue from the same population. A blended cost against a single-market revenue figure is two populations wearing one number.

Corrections

What was believed, and what replaced it

A green Pages run plus a matching CSS hash means the deploy is current.

The deployed JS chunk did not match the local build, and that looked like the repo's recorded staleness trap firing. It was not. CI injects build variables the local build lacks, so content and therefore hash differ legitimately — while the CSS hash matched exactly, which made the mismatch look worse than it was. Comparing a deployed hash against a local build proves nothing. Probe the deployed bundle for a feature shipped in a known commit instead.

Sending is blocked on building transport.

It was blocked on the transport already built never having had an address to send to: one of 24 draft call sites passed a vendor id, and zero of 126 seeded vendors carried an email. The send button rendered on no event in the app.
